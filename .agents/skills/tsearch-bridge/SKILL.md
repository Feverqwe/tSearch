# Bridge в tSearch

Bridge — тестовое расширение для Chrome и клиент для Node.js/Jest. В живом режиме Native Messaging передаёт запрос в Chrome стенда, а ответ возвращается в Node.js как `Response`. Выбирай контекст под сценарий tSearch: `extension` для прямого запроса, `tab` для запроса с сессией открытой вкладки, когда в профиле tSearch включена поддержка прокси. tSearch в режиме прокси открывает временную вкладку сам; живой Bridge использует уже открытую. Разбор результатов проверяй отдельно через tSearch.

## Сборка и запуск

Следуй [инструкции Bridge](../../../test/bridge/README.md) по установке, разрешённым адресам и перезагрузке. После пересборки дождись нового подключения.

## Работа агента

- Переиспользуй открытый обычный Chrome с профилем стенда. Для режима `tab` открой сайт в том же профиле по [руководству запуска](../../../docs/development.md#проверка-в-браузере). Пользователь проходит вход и проверку сайта вручную. Оставляй вкладку открытой.
- Для GET используй `TSEARCH_BRIDGE_CONTEXT=extension TSEARCH_BRIDGE_URL='<URL>' npm --prefix test/bridge run test:live` в прямом режиме или `TSEARCH_BRIDGE_CONTEXT=tab` в режиме вкладки (это режим живого Bridge по умолчанию). Для POST или проверки тела ответа используй `connectLiveBridge().fetch(url, {requestContext, ...options})` из `test/bridge/live.cjs`. При сравнении меняй только контекст; передавай те же URL, метод, заголовки и тело, что и tSearch. Для ответа с legacy-кодировкой используй `arrayBuffer()` и `TextDecoder` с кодировкой из `Content-Type`.
- Если Bridge недоступен, проверь значок `ON`, активный профиль стенда и установку расширения из текущего checkout. После сборки или смены checkout проверь, была ли перезагружена его карточка. Само наличие файла подключения ещё не подтверждает, что Chrome отвечает.
- Если Bridge просит открыть сайт, проверь, что открыта загруженная вкладка с тем же origin, включая схему и порт. Если сайт вне конфигурации Bridge, сверь разрешённые хосты и собери расширение для нужных адресов по README. Сохраняй доступ к ранее настроенным хостам, если они ещё нужны.
- HTTP 403 или страница Cloudflare означают ответ сайта, если вызов `fetch` вернул `Response`. HTTP 200 тоже может содержать форму входа или пустую оболочку. Проверяй конечный адрес и ожидаемую структуру ответа. В выводе оставляй статус и нужные признаки. Куки, токены, персональные данные, исходный HTML и HAR не сохраняй в репозитории.
- Если нужна повторяемая проверка без внешнего сайта, используй локальный сервер и изолированный режим `launchBridge` из README. Для изменений самого Bridge прогони `npm --prefix test/bridge test` и, когда соединение доступно, проверь живой запрос отдельно.
